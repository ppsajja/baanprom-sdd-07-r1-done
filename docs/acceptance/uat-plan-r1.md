# แผนตรวจรับ R1 บ้านพร้อม (UAT plan)

รุ่น 1.0 | สถานะ: ใช้จริง (ร่างแรก 2 พ.ย. 2569 ปรับหลังประชุม EV-048 วันที่ 3 พ.ย. 2569) | เจ้าของแผน: RE lead (กลุ่ม X) | ผู้อนุมัติแผน: SH-01
แบบเอกสาร: test plan ตาม ISO/IEC/IEEE 29119-3:2021 ส่วนการตรวจรับ (บทเสริม การตรวจรับและการส่งมอบ หัวข้อ 1.3)
ที่มา: หน้าบทเรียน RE in One Line และการตรวจรับ หัวข้อ 6.3 (แผนตรวจรับรุ่นแรกของบ้านพร้อม) ปรับให้อ้าง Baseline ที่มีจริงใน repo นี้
ข้อมูลทุกอย่างในเคสนี้เป็นข้อมูลสมมติเพื่อการสอน

## 1. อ้างอิง (จะเทียบกับอะไร)

- Baseline B4 (docs/srs/baseline.md 31 ต.ค. 2569) บวก CR-10 และ CR-02 ที่อนุมัติแล้วใน EV-048 (3 พ.ย. 2569)
- หน้าบทเรียนตัวอย่างเขียนว่า "อ้างอิง Baseline B2" เพราะตอนนั้นยังมีแค่ B2 แผนจริงต้องอ้างรุ่นล่าสุดที่อนุมัติ ถ้ามีคนถามว่า "ตกลงกันไว้ว่าอย่างไร" คำตอบอยู่ที่ B4 กับ CR-10 ไม่ใช่ความจำของใคร
- ถ้าตรวจรับผ่าน รุ่นนี้จะประกาศเป็น Baseline B5 (B4 + CR-10 + CR-02 + การแก้ข้อบกพร่องที่พบระหว่างตรวจ)

## 2. ขอบเขต

ตรวจรับ: feature การจอง สถานะงาน และการยกเลิกคืนเงิน (specs/002-booking, 003-job-status, 004-cancel-refund) และข้อกำหนดข้ามทุก feature ในไฟล์กลางส่วน 6 (AC-00-01 ถึง AC-00-08)
ตรวจแยก: ผู้ช่วยตอบคำถามและเลื่อนนัด UC-14 (specs/005-ai-assistant) ใช้เกณฑ์จบของตัวเองในส่วน 9 เพราะ B4 เขียนไว้ว่าผู้ช่วยเปิดใช้แยกได้ (ปุ่มหยุด REQ-AI-022)
ตรวจด้านปฏิบัติการ: แผนแยกใน docs/acceptance/oat-plan-r1.md ผู้ลงนามคือ Ops lead

ไม่ใช่เกณฑ์ของรอบนี้ (ผู้ตรวจเห็นได้ แต่ไม่ใช้ตัดสินรับ)
- การลงทะเบียนและเข้าสู่ระบบ UC-01 UC-02 การจับคู่ช่างใหม่ UC-05 การให้คะแนน UC-11 และการจองหรือยกเลิกแทนโดย call center (UC-07 A2) เลื่อนไป R2 ตาม EV-044
- คิวรอ (waitlist) และข้อเสนอเมื่อไม่มีช่างว่างใน 7 วัน (Q-28, Q-33) เลื่อนไป R2
- ข้อเสนอที่ยังไม่อนุมัติ: REQ-UX-002, REQ-QA-005 และคำขอใด ๆ ที่เกิดระหว่างตรวจรับ (บันทึกเป็น CR ใหม่ ไม่ใช่ข้อบกพร่อง)
- REQ-OP-001 (นาทีล่มรายเดือน) วัดได้หลังเปิดใช้จริงเท่านั้น ย้ายไปเป็นเงื่อนไขของช่วง hypercare
- การเปิดให้ลูกค้าจริง: R1 ยังตรวจเจ้าของงานด้วยรหัสที่ผู้ขอส่งมาเอง (TH-01) การรับ R1 คือการรับมอบระบบ ส่วนการเปิดให้ลูกค้าจริงรอการเข้าสู่ระบบใน R2 (EV-048)

## 4. ข้อมูลทดสอบ

- ลูกค้าสมมติ 30 ราย ("ลูกค้าทดสอบ 01" ถึง "30") ช่างสมมติ 10 คน ("ช่างทดสอบ 01" ถึง "10") ช่วงเวลาว่าง 7 วันข้างหน้า วันละ 3 ช่วงต่อช่าง และช่วงวันนี้อีก 1 ช่วงต่อช่าง สร้างด้วย backend/uat_seed.py
- ไม่มีเบอร์จริงของใคร เบอร์ทุกเบอร์ขึ้นต้นด้วย 000-000 ที่อยู่เป็น "บ้านทดสอบเลขที่ n" REQ-PRV-002 ใช้กับการทดสอบด้วย ไม่ใช่แค่ระบบจริง
- เมื่อจบรอบ ลบฐานข้อมูลทดสอบทั้งฐาน ไม่ย้ายข้อมูลทดสอบไปใช้ต่อ

## 5. สภาพแวดล้อม (test environment readiness)

เครื่องทดสอบที่ตั้งค่าเหมือนระบบจริง ไม่ใช่เครื่องของนักพัฒนา
- ติดตั้งจาก export สะอาดของ commit ที่ส่งตรวจ ด้วยคำสั่งใน docs/handover/install-guide.md (OAT-1 ตรวจขั้นนี้)
- APP_ENV=production (หน้า /docs ปิด ช่อง now= ถูกเพิกเฉย endpoint ของ ops ต้องมี X-Ops-Token) OPS_TOKEN ของเครื่องทดสอบ
- ฐานข้อมูล PostgreSQL 16 (D-00-02) ไม่ใช่ SQLite
- ระบบภายนอกยังเป็นตัวจำลอง (บอกผู้ตรวจก่อนเริ่ม): Payment Gateway (FakeGateway) ระบบส่งข้อความ (FakeNotifier) LLM (MockLLM) ผู้ตรวจดูข้อความแจ้งเตือนจากคิว (GET /notifications/queue) แทนโทรศัพท์
- หน้าจอ: frontend build แล้วเปิดผ่านเบราว์เซอร์บนคอมพิวเตอร์และมือถือ 1 เครื่อง
ช่องว่างชนิด env ที่ยอมรับไว้ก่อน: เครื่องทดสอบเป็นเครื่องเดียว (หลังบ้าน ฐานข้อมูล และผู้ยิงโหลดอยู่เครื่องเดียวกัน) ผลทดสอบโหลดจึงเป็นค่าที่เครื่องนี้ทำได้ ไม่ใช่ค่าของระบบจริง

## 6. เกณฑ์เริ่ม (entry criteria)

ผู้ตรวจไม่ควรเป็นคนแรกที่เจอว่า test ไม่ผ่าน ทุกข้อต้องผ่านก่อนเชิญผู้ตรวจ

1. test ทั้งชุดผ่านด้วยคำสั่งเดิมจาก export สะอาด Python 3.11 และ 3.12 และ vitest ไม่มี test ข้าม บันทึกใน specs/000-shared/test-run.txt
2. ตารางตามรอย (rtm.md ของ 002, 003, 004 และ 000-shared) ไม่มีสายขาดในข้อระดับ Must
3. หน้าจอตรง mockup 42 จาก 42 ตามที่ทีมตรวจเอง (การตรวจ 6 ข้อต่อหน้า 7 หน้า)
4. ไม่มีข้อบกพร่องระดับวิกฤตหรือสูงค้างอยู่ใน gaps.md
5. ทีมเดินซ้อมทุก scenario ผ่าน API บนเครื่องทดสอบด้วย backend/uat_replay.py ผ่านทุกข้อ
6. คำถามที่เป็นเงื่อนไขก่อนเปิด R1 มีคำตอบและทำแล้ว (CR-10)

## 7. ระดับความรุนแรงและลำดับการแก้ (ตกลงก่อนเริ่ม ไม่ตั้งตอนเจอ)

ตารางเดียวกับบทเสริม การตรวจรับและการส่งมอบ หัวข้อ 3.2 ผู้ให้ระดับความรุนแรงคือ RE lead (ผู้คัดแยก) โดยตอบคำถามในคอลัมน์ที่สอง ผู้ตัดสินลำดับการแก้คือ SH-01

| ระดับ | คำถามที่ใช้ตัดสิน | ตัวอย่างในบ้านพร้อม | ผลต่อการตรวจรับ |
|---|---|---|---|
| วิกฤต | เงินผิด ข้อมูลรั่ว หรืองานหลักทำไม่ได้เลย และไม่มีทางเลี่ยง | ตัดมัดจำซ้ำ หรือช่างเห็นเบอร์ลูกค้าของงานที่ไม่ใช่ของตน | ไม่รับ |
| สูง | งานหลักทำได้ แต่ผิดกฎธุรกิจ หรือต้องมีคนช่วยทุกครั้ง | คืนเงินไม่ตรงกับกฎ BR-01 ตามเวลาที่ยกเลิก | ไม่รับ จนกว่าจะแก้และตรวจซ้ำ |
| กลาง | ทำงานถูก แต่ผู้ใช้อาจเข้าใจผิด หรือต้องถามคนอื่นเพิ่ม | หน้ายืนยันการจองไม่บอกเวลาที่ต้องชำระมัดจำให้เสร็จ | รับแบบมีเงื่อนไข พร้อมผู้รับผิดชอบและวันแก้ |
| ต่ำ | ความสวยงามหรือคำสะกด ที่ไม่ทำให้เข้าใจผิด | ปุ่มสองปุ่มไม่ตรงแนวกัน | รับ แล้วแก้ในรุ่นถัดไป |

| ลำดับการแก้ | ความหมาย |
|---|---|
| ด่วน | ต้องแก้ก่อนลงนาม หรือก่อนเปิดให้ผู้ใช้จริง |
| ปกติ | แก้ในรอบแก้ไขที่วางแผนไว้ หรือในช่วง hypercare |
| รอได้ | เข้ารายการของรุ่นถัดไป |

สิ่งที่พบระหว่างตรวจแยกเป็นสามชนิดด้วยคำถามเดียวว่า "B4 กับ CR-10 เขียนไว้อย่างไร"
- เขียนไว้ แต่ระบบไม่ทำตาม คือ ข้อบกพร่อง (DEF-nn) ทีมแก้
- ไม่เคยเขียน คือ คำขอเปลี่ยนแปลง เขียน CR วิเคราะห์ผลกระทบ แล้วจัดลำดับ ไม่ทำให้รอบนี้ไม่ผ่าน
- เขียนไว้ ระบบทำตาม แต่สิ่งที่เขียนผิด คือ สเปกผิด แก้สเปกก่อนผ่าน CR แล้วจึงแก้ระบบ และย้อนหาว่าข้อความเดิมมาจากไหน

## 8. เกณฑ์จบ (exit criteria) ของ 002 ถึง 004

1. AC ระดับ Must ของ 002, 003, 004 และ AC-00-nn ผ่านทุกข้อ เมื่อผู้ตรวจเดินบนหน้าจอจริง (AC ที่ไม่มีหน้าจอ ผู้ตรวจดูผลบนเครื่องทดสอบกับ Dev lead) รายการ scenario อยู่ใน docs/acceptance/uat-scenarios-r1.md
2. รายการต้องตรงของส่วน 12 ทั้ง 7 หน้า 48 จาก 48 (UI-07-01 6, UI-07-02 8, UI-07-03 5, UI-09-01 6, UI-09-02 5, UI-08-01 10, UI-08-02 8)
3. ไม่มีข้อบกพร่องระดับวิกฤตหรือสูงค้าง ระดับกลางมีแผนแก้ ผู้รับผิดชอบ และวันเสร็จ
4. ข้อที่ตรวจได้แค่แบบย่อส่วน เขียนเป็นเงื่อนไข ไม่นับว่าผ่าน: AC-07-08 (ลูกค้า 500 คน test ย่อส่วน 20 คำขอ T-09) และ AC-09-12, AC-08-09 (50 คน test ย่อส่วน 10 คำขอ) วัดเต็มรูปบนเครื่องทดสอบด้วยการยิงโหลด
5. OAT ผ่านตาม docs/acceptance/oat-plan-r1.md (Ops lead ลงนามแยก)

## 9. ผู้ช่วย UC-14 (ตรวจแยก)

เกณฑ์จบของผู้ช่วยมาจาก B4 และ specs/005-ai-assistant/quality-requirements.md ส่วน 3 ไม่มีเกณฑ์ใหม่
- ชั้นที่ 1 eval: ผ่าน 20 จาก 20 เกณฑ์ กับ LLM ตัวจริงที่ผ่านเงื่อนไข Q-56 (ผลกับ MockLLM เป็นหลักฐานของรั้วและวิธีวัดเท่านั้น)
- เกณฑ์ที่ต้องใช้คน: AC-14-03 คนตรวจ 30 ข้อ AC-14-09 และ AC-14-12 ผู้ใช้ 20 คน
- ซ้อมปิดผู้ช่วยจับเวลา ภายใน 5 นาที โดยไม่ deploy (AC-14-14, REQ-AI-022) ทำเป็น OAT-7
- ผลที่เป็นไปได้: รับ (ผ่านทุกชั้น) รับแบบมีเงื่อนไข หรือไม่รับในรอบนี้ ถ้าไม่รับ ผู้ช่วยต้องปิดในระบบที่ส่งมอบ
